## 1. 一句话总结

> 本文发现五种主流抗探测代理协议（obfs4、Shadowsocks、Lampshade、MTProto、OSSH）在面对主动探测时存在独特的 TCP 行为指纹（响应数据、连接超时、缓冲区阈值），可通过少量精心构造的探测包以极低误报率识别代理服务器，并提出"无限超时"等防御建议。

---

## 2. 核心贡献

### 2.1 贡献列表

1. **发现抗探测代理的根本性漏洞**：即使代理服务器对探测不返回应用层数据，其 TCP 层行为（超时时间、FIN/RST 关闭阈值）仍可被用于指纹识别，覆盖 obfs4、Shadowsocks、Lampshade、MTProto、OSSH 五种协议。

2. **提出三维度指纹特征体系**：识别出三个关键区分维度——响应数据（Response Data）、连接超时（Timeouts）、缓冲区阈值（Buffer Thresholds，含 FIN threshold 和 RST threshold），并首次发现应用层特定的 TCP 关闭阈值可作为远程指纹。

3. **大规模实证验证**：在 190 万+端点的真实互联网数据集上验证攻击有效性，误报率保守估计低于 0.001%（MTProto 除外），并与代理开发者合作确认发现。

4. **提出并评估防御策略**：建议代理采用"无限超时"策略（不关闭连接），并基于 ISP Tap 数据集分析了最佳有限超时伪装值，已推动 Psiphon、obfs4、Outline、Lampshade 等项目部署修复。

5. **揭示 MTProto 的"有效隐身"特性**：MTProto 的"永远不关闭连接"策略使其与互联网上约 0.56%（Tap）/ 0.02%（ZMap）的端点行为一致，为其他代理协议提供了防御范本。

| 整体误报率 | — | < 0.001% | MTProto 除外 |

### 4.2 关键发现

1. **"无响应"即指纹**：在 ISP Tap 数据集中，94% 的端点至少对一种探测返回数据。代理服务器对所有探测均无数据响应，这种"完全沉默"在互联网上极为罕见，是首要筛选维度。

2. **TCP 关闭阈值是实现级指纹**：每种代理协议有独特的 FIN/RST 关闭阈值（如 obfs4: 8-16KB, OSSH: 24/25 bytes, Shadowsocks: 50/51 bytes, Lampshade: 256/257 bytes），可精确区分实现。这些阈值源于应用层 recv buffer 大小和解析逻辑，是首次被远程测量的应用层 TCP 特征。

3. **超时分布高度集中**：82% 的端点超时值集中在前 10 个常见超时值（10, 15, 20, 30, 60, 300 秒等），随机超时策略反而会将代理暴露到极小的端点群中。

4. **MTProto 的"无限超时"是最佳伪装**：MTProto 永不关闭连接的策略使其与互联网上约 0.56% 的端点行为一致，虽然仍有误报但远低于其他协议。

5. **ZMap 数据集含大量防火墙诱饵**：42% 的 ZMap 端点表现出相同的"永不响应、永不关闭"行为，这是防火墙的 "CyberChaff" 策略，降低了 ZMap 数据集的有效多样性。

## 7. [深度分析] 方法设计详解

### 7.1 方法整体流程

本文的检测方法遵循"排除-确认"两阶段流程：

1. **排除阶段（Exclusion）**：向目标端点发送多种协议探测包，若端点对任意探测返回应用层数据，则立即排除为非代理。此步骤可过滤 94% 的 Tap 数据集端点。

2. **确认阶段（Confirmation）**：对剩余未排除端点，通过决策树分析其 TCP 行为（超时时间、FIN/RST 关闭阈值），逐协议确认是否为代理。

### 7.2 详细 Pipeline

| 步骤 | 输入 | 具体操作 | 输出 | 作用 |
|---|---|---|---|---|
| 1. 探测发送 | 目标 IP:Port 列表 | 发送 13 种探测（7 种协议 + 6 种随机长度） | 响应数据、关闭类型、关闭时间 | 收集端点行为特征 |
| 2. 数据响应过滤 | 探测结果 | 检查是否有任意探测返回数据 | 非代理候选集（94% 被排除） | 快速排除大量非代理端点 |
| 3. 阈值检测 | 未排除端点 | 二分搜索 FIN/RST 关闭阈值 | 每端点的 FIN threshold 和 RST threshold | 获取应用层 TCP 指纹 |
| 4. 决策树分类 | 端点行为特征 | 按协议特定决策树逐层判断 | 代理/非代理标签 | 精确识别代理服务器 |
| 5. 人工验证 | 分类结果 | 联系开发者确认、分析端点其他端口 | 确认/排除 | 降低误报，验证方法有效性 |

### 7.3 模型结构或系统模块

| 模块 | 功能 | 输入 | 输出 | 与其他模块关系 |
|---|---|---|---|---|
| 探测生成器 | 生成 13 种探测包 | 探测配置 | TCP 连接 + 探测数据 | → 响应收集器 |
| 响应收集器 | 记录端点响应行为 | 探测结果 | 响应数据/关闭类型/时间 | → 过滤器 + 阈值检测器 |
| 数据响应过滤器 | 排除有数据响应的端点 | 响应数据 | 非代理候选集 | → 阈值检测器 |
| 阈值检测器 | 二分搜索 FIN/RST 阈值 | 未排除端点 | FIN/RST threshold 值 | → 决策树 |
| 协议决策树 | 按协议特征分类 | 行为特征向量 | 代理/非代理标签 | → 人工验证 |
| 超时分析器 | 分析最佳伪装超时值 | 超时分布数据 | 推荐超时策略 | 用于防御建议 |

### 7.4 公式、算法和机制解释

**TCP 关闭阈值机制（核心发现）**：

当服务器应用调用 `recv()` 读取客户端数据时，内核将数据放入 socket buffer。如果应用解析失败后调用 `close()`：
- 若 buffer 中**无未读数据** → 内核发送 `FIN`（正常关闭）
- 若 buffer 中**有未读数据** → 内核发送 `RST`（异常关闭）

因此，FIN threshold < RST threshold，两者之差反映了应用的 recv buffer 大小。例如 obfs4 的 recv buffer 为 1448 字节，导致 RST threshold = FIN threshold + (1448 - FIN threshold mod 1448)。

**二分搜索阈值检测算法**：

```
1. 发送 4096 字节随机数据，观察 3 秒内是否关闭
2. 若关闭：减半字节数，重复直到不关闭 → 获得下界
3. 若不关闭：翻倍字节数（至 1MB），重复直到关闭 → 获得上界
4. 在上下界之间二分搜索精确阈值
5. 用 3 种不同种子验证阈值稳定性
```

**超时伪装分析**：

论文分析了 ISP Tap 数据集中"探测无关"（probe-indifferent）端点的超时分布，发现：
- 最常见行为是"永不超时"（300 秒 TIMEOUT），占 0.7%（Tap）/ 42%（ZMap）
- 有限超时中最常见的是立即关闭（FIN/RST at 0s），但需确保对所有探测一致
- 随机超时值（如 74 秒）反而暴露代理，因为只有 0.02% 的端点使用该值

## 8. [深度分析] 实验详细分析

### 8.1 实验设计和设置

**数据集构建**：
- **ISP Tap 数据集**：从科罗拉多大学 10 Gbps 路由器被动采集 3 天 netflow 数据，获得 55 万+唯一服务器端点，其中 433,286 个接受连接（SYN-ACK 响应率 79%）
- **ZMap 数据集**：向 20,000 个随机 IP 的所有 TCP 端口（0-65535）发送 SYN，获得 150 万端点
- **代理端点**：obfs4 20+个（BridgeDB）、Lampshade 3个（开发者提供）、OSSH 3个（Psiphon）、MTProto 3个（Telegram）、Shadowsocks 2个（自建 + Outline）

**探测协议**：HTTP GET、TLS Client Hello、Modbus、S7、DNS AXFR、STUN、随机字节（23B-17KB）、空探测

### 8.2 数据集详情

| 数据集 | 规模 | 来源 | 特点 |
|---|---|---|---|
| ISP Tap | 433k 端点 | 被动采集 10Gbps 路由器 | 代表性强、多样性高（129k 唯一响应组） |
| ZMap | 1.5M 端点 | 主动扫描随机 IP:Port | 规模大但含 42% 防火墙诱饵、多样性低（31k 唯一响应组） |
| 代理端点 | ~30 个 | 分发系统/开发者/自建 | 样本量有限但覆盖主流协议 |

### 8.3 Baseline 选择理由

本文不与传统分类器比较，而是：
- **手动决策树 vs 自动决策树**：手动树基于源码分析构建，自动树基于 scikit-learn 训练。两者准确率相近（手动略优），但手动树更易解释和维护。
- **代理行为 vs 互联网基线**：将代理行为与 190 万真实端点比较，评估"伪装难度"。

### 8.4 消融实验

论文通过逐步增加探测类型展示了探测覆盖的影响：
- 初始 6 种探测 → 仍有数百端点与 obfs4 行为相同
- 增加 DNS AXFR 探测 → 排除 DNS 服务器误报
- 增加 STUN 探测 → 排除 Cisco WebEx 设备误报
- 最终 8 种协议探测 + 5 种随机长度 → 实现零/近零误报

### 8.5 Case Study / 可视化分析

**obfs4 决策树示例**（Figure 3）：
1. 发送 17KB 随机数据 → 若 2 秒内收到 RST → 进入下一层
2. 检查所有其他探测 → 若全部在 30-90 秒内以 FIN 关闭 → 判定为 obfs4

**原因**：obfs4 的 FIN threshold 为 8-16KB（随机），17KB 探测超过 RST threshold 触发立即 RST；其他探测（均 < 8KB）在 close threshold 之下，等待 closeAfterDelay 超时（30-90 秒随机）后以 FIN 关闭。

**MTProto 的"隐身"效果**（Figure 8）：
- 决策树仅检查"所有探测是否均超时"
- 导致 3144 个 Tap 端点被误标为 MTProto
- 但这也说明"永不响应"策略确实使 MTProto 融入了互联网的"长尾"行为

### 8.6 局限性与失败案例

1. **MTProto 分类困难**：0.56% 的 Tap 端点与 MTProto 行为完全一致，无法区分
2. **代理样本有限**：每种协议仅 1-20 个端点，统计代表性受限
3. **数据集偏差**：Tap 数据集来自美国大学网络，可能不代表全球互联网分布
4. **时间窗口**：数据采集仅 3 天，端点行为可能随时间变化
5. **未考虑自适应代理**：若代理动态调整超时/阈值行为，决策树可能失效

```
验证：190 万端点实证 + 开发者确认 + 自动分类器对比
     ↓
防御：无限超时策略 + 最佳有限超时值推荐 + 开发者合作部署
```

### 13.3 创新模块详解

**模块一：TCP 关闭阈值远程测量**
- **创新点**：首次提出应用层特定的 FIN/RST 阈值可作为远程指纹
- **原理**：应用 recv buffer 大小 + `close()` 时内核对未读数据的处理逻辑
- **测量方法**：二分搜索 + 3 种种子稳定性验证
- **意义**：即使两种协议超时相同、均无数据响应，仍可通过阈值区分

**模块二：探测无关端点（Probe-indifferent Endpoints）分析**
- **创新点**：识别出对所有探测响应一致的端点子集，作为代理最佳伪装目标
- **分析**：6,956 个 Tap 端点（1.6%）对所有探测响应一致
- **应用**：指导代理选择最佳伪装超时值

**模块三：防御策略量化评估**
- **创新点**：不仅提出防御建议，还量化评估每种策略的伪装效果
- **策略**：无限超时 > 立即 FIN > 常见有限超时 > 随机超时
- **影响**：推动 Psiphon、obfs4、Outline、Lampshade 实际部署修复
